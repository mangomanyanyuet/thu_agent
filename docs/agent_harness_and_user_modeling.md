## —— 面向「5 分钟视频语音情绪陪伴 Agent」的三章调研

- **调研时间**：2026-09
- **配套文档**：`情绪识别陪伴Agent_PRD_2.md`（产品需求，下称 **PRD**）、`docs/prd_gap_75.md`（7.1 超时收尾 / 7.5 风险处理补齐）、`docs/agent_framework_research.md`（下称 **选型报告**）

  2. 基于 PRD v1.0 的**单次 5 分钟**会话场景，Agent 框架怎么选？Agent 需要哪些能力？场景需求如何映射到技术能力？
  3. 冷启动用户（零历史）如何做画像建模与主动提问？

## 0. 结论先行（TL;DR）

| 章节 | 核心结论 |
|---|---|
| **一、Harness 六元组** | 六元组给出了"模型之外一切"的**最小完备分解**。与 ETCLOVG 的差别是：六元组把 **S（状态存储）单列**，而 **O（可观测）与 G（治理）未被显式覆盖**。用 LTS 语义区分**安全性（不变量）与活性（最终进展）**，是本项目治理设计最有用的一件工具 |
| **二、框架选型** | **LangGraph 保留，但必须按 PRD 场景"瘦身"**。PRD 是 5 分钟单次会话，**不需要**长期记忆与时间旅行（二期才要）。真正的瓶颈不是框架，是 **LLM 推理（实测 10s，PRD 要求 <2s）**。ADK 只在"要做实时边说边出字"时才值得评估 |
| **三、冷启动与主动提问** | 冷启动的实质是**在 3-4 轮的极稀缺提问预算内，最大化信息增益**。推荐**三阶段路线**：先验温启动 → **PRIME 式无梯度记忆进化** → 受约束的 RL。**优先无梯度方案**，因为记忆库可解释、可审计、可人工修正 —— 这在心理健康合规场景优于端到端最优 |

> **贯穿三章的一条主线**：PRD 的 5 分钟单次会话与选型报告假设的"长期每日陪伴"是**两个不同产品**。选型报告推荐 LangGraph 的主要理由（checkpointer 时间旅行、跨天长期记忆）在 PRD 场景下**暂不生效**；真正生效的只有"状态机 + 条件分支 + 硬中断"三项。本章据此重新论证。

# 第一章 《Agent Harness for LLM Agents: A Survey》与形式化六元组

> 姊妹综述：Meng et al.《Agent Harness for LLM Agents: A Survey》。与选型报告 §3 引用的 Li et al.《Agent Harness Engineering: A Survey》（ETCLOVG 七层）是同一对象的两种刻画，可交叉印证。

## 1.1 为什么需要"Harness"这个概念

综述要解决的问题是：业界说"Agent 不够可靠"时，"Agent"到底指什么？模型、提示词、工具、记忆、还是那套循环？概念不清导致失败无法归因。

综述给出的工作定义：

> **Harness = Agent 系统里除模型权重之外的一切。**

具体包括执行环境、工具接口、状态与记忆、生命周期编排、可观测、验证、治理。

这个概念划分的工程价值在于**归因**：当系统出错时，可以先判断"是模型的错还是 harness 的错"，而不是笼统地归咎于模型能力。选型报告 §3.1 的实证支撑是：**长时程任务的基准分数是「模型–harness 配对」的属性，而非模型单独的属性**；harness-only 消融实验中，仅改工具格式与调用协议，编码基准改善可达 10 倍量级。

落地成两条纪律：**换模型必须做 harness 固定的对照实验**；**先怀疑 harness，再怀疑模型**。

## 1.2 形式化六元组 \(H = (E, T, C, S, L, V)\)

| 符号 | 组件 | 职责 | 回答的问题 |
|---|---|---|---|
| **E** | 执行循环 Execution loop | 观察–思考–行动循环、终止判定、错误恢复 | 谁驱动、何时停、错了怎么办 |
| **T** | 工具注册表 Tool registry | 类型化目录、路由、监控、schema 校验 | 外部能力怎么被发现与调用 |
| **C** | 上下文管理器 Context manager | 窗口管理、压缩、检索 | 每步模型看得到什么 |
| **S** | 状态存储 State store | 跨轮次/会话持久化、崩溃恢复 | 什么被记住、从哪恢复 |
| **L** | 生命周期钩子 Lifecycle hooks | 授权、日志、策略执行、埋点 | 在哪插入管控而不改推理逻辑 |
| **V** | 评估接口 Evaluation interface | 动作轨迹、中间状态、成功信号 | 怎么判断做对了、错在哪 |

### 1.2.1 单步转移的形式化

综述用标记转换系统（LTS）刻画 harness 的一步。设第 \(t\) 步的观察为 \(o_t\)、持久化状态为 \(s_t\)、模型策略为 \(\pi\)，则：

\[
\begin{aligned}
c_t        &= C(s_t \oplus o_t)                    && \text{上下文装配} \\
\hat{c}_t  &= L_{\text{pre}}(c_t)                  && \text{执行前钩子} \\
a_t        &= \pi(\hat{c}_t)                       && \text{模型推理} \\
\tau_t     &= T.\text{route}(a_t)                  && \text{工具路由} \\
\tilde{\tau}_t &= L_{\text{pre-invoke}}(\tau_t)     && \text{调用前钩子} \\
o_{t+1}    &= \text{exec}(\tilde{\tau}_t)          && \text{工具执行} \\
o'_{t+1}   &= L_{\text{post-invoke}}(o_{t+1})      && \text{执行后钩子（过滤）} \\
s_{t+1}    &= E.\text{update}(s_t, a_t, o'_{t+1})  && \text{状态更新} \\
r_t        &= V(s_t, a_t, o'_{t+1})                && \text{评估信号}
\end{aligned}
\]

这个式子的价值在于**把"哪里可以插入管控"变成了有穷清单**：\(L\) 的四个挂载点（pre-execution / pre-invocation / post-execution / HITL）恰好是治理的全部可选位置。选型报告 §3.3 把它映射成了本项目的具体用法：

| 钩子 | 位置 | 本项目用法 |
|---|---|---|
| 执行前 pre-execution | 输入进 LLM 前 | 硬注入 `risk_flags`、危机话术约束、非医疗定位声明 |
| 调用前 pre-invocation | 工具执行前 | 「通知人工 / 推送热线」二次确认，防误触发 |
| 执行后 post-execution | 工具输出回注前 | 过滤自杀方法、手段可得性等禁止内容 |
| 人工介入 HITL | 高风险动作 | high / imminent 分支 `interrupt()` 挂起 |

**关键设计收益**：治理通过钩子注入，**不修改 Agent 核心推理逻辑**。这与选型报告 §8.1「风险检测与对话生成解耦」是同一判断的两种表述。

### 1.2.2 S 为什么单列

六元组把 **S（状态存储）** 从 C 里分出来，是相对于 ETCLOVG 最重要的一处差异。理由：

- **C 是"每步看到什么"**，是**视图**（view），可以重算、可以丢弃、可以压缩；
- **S 是"什么被记住"**，是**事实**（fact），不可重算、崩溃后要从这里恢复。

对本项目这条区分是刚需：滚动摘要（C）可以被压缩甚至丢弃，但 `risk_flag`（S）**永不压缩、永不摘要**。把两者混为一谈，就会出现"危险信号被摘要管道吃掉"的事故。选型报告 §3.6 开放问题 #2 的表述是：**恢复时应从持久化制品（`risk_flags`、量表时序）恢复，而不是从压缩后的摘要恢复**。

## 1.3 与 ETCLOVG 七层的映射

| 六元组 | ETCLOVG | 说明 |
|---|---|---|
| E 执行循环 | **E** 执行环境 + 部分 **L** 编排 | 六元组的 E 偏"循环"，七层的 E 偏"边界/沙箱" |
| T 工具注册表 | **T** 工具接口与协议 | 一致 |
| C 上下文管理器 | **C** 上下文与记忆（视图部分） | 一致 |
| **S 状态存储** | 归入 **C / L** | ⚠ 七层**未单列**，这是六元组的补充 |
| L 生命周期钩子 | **G** 治理 + **O** 可观测 | 钩子是 G/O 的实现机制 |
| V 评估接口 | **V** 验证与评估 | 一致 |
| — | **O** 可观测 | ⚠ 六元组**未显式覆盖** |
| — | **G** 治理与安全 | ⚠ 六元组**未显式覆盖**（只给了实现手段 L） |

**读法**：两个框架是互补而非竞争。六元组更形式化、更贴近实现（可直接对应代码模块）；七层更贴近**组织分工**（"谁负责这一层"）。选型报告 §3.3 指出，七层把 O 与 G 提升为独立层，正是因为生产环境中"这两层各有独立工具栈、各自由不同团队负责"。

本项目建议：**用六元组做代码架构，用 ETCLOVG 做团队分工与自检清单**。

## 1.4 LTS 语义：安全性 vs 活性

综述用标记转换系统区分两类性质，这个区分对本项目的治理设计最有用：

\[
\text{安全性（Safety）} = \Box P \quad \text{任何可达状态都满足 } P
\]
\[
\text{活性（Liveness）} = \Diamond Q \quad \text{最终会到达 } Q
\]

一句话：**安全性是"不能出错"，活性是"不能不动"。**

### 本项目的不变量与活性目标

**安全性（不变量，违反即事故）**

- \(\Box\) 风险相关表达永不进入摘要/压缩管道
- \(\Box\) high 及以上必须挂起等人工，不做自动化闭环
- \(\Box\) 绝不输出自杀方法、手段可得性、对自伤行为的中立/美化描述
- \(\Box\) 绝不输出诊断性结论（PRD §1 非目标）
- \(\Box\) 对话中绝不口头播报情绪判断结论（PRD §9.1）
- \(\Box\) Tier 3 字段绝不通过界面呈现给用户（PRD §9.2 硬性规定 2）

**活性（最终进展，违反即系统"卡死"或"沉默失败"）**

- \(\Diamond\) 危机分支必须给出热线，不允许静默失败
- \(\Diamond\) 每轮必须有风险分级结果，不允许无响应
- \(\Diamond\) 累计 ≥ 5:30 必须进入结束语（PRD 补齐 §7.1 硬上限）
- \(\Diamond\) 沉默 > 8s 必须有主动确认话术（PRD 补齐 §7.1）
- \(\Diamond\) LLM 超时/异常时必须返回兜底话术 + 热线（选型报告 §8.4 红线 4）

> **为什么必须同时约束两者**：只做安全护栏而不做降级兜底，会产出一个"什么都不敢说"的 Agent —— 它满足所有 \(\Box P\)，却在用户最需要回应时沉默。选型报告 §3.9 的表述是："只做安全护栏而没做降级兜底，会产出一个『什么都不敢说』的 Agent。"

## 1.5 Harness 完备性矩阵

| 类别 | 代表系统 | 特征 |
|---|---|---|
| 全栈 harness（各层齐备） | Claude Code、AIOS、OpenHands、SWE-agent | 真正的生产级执行器 |
| 多智能体 harness | AutoGen、MetaGPT、CAMEL、ChatDev | 协同强，但 E / C / V 层参差 |
| **通用编排框架** | **LangChain、LangGraph、LlamaIndex** | **只提供原语，完备性完全取决于使用者怎么拼** ← 我们在这一格 |
| 评估基础设施 | AgentBench、OSWorld、BrowserGym、HAL | 只覆盖 V 层，不是执行 harness |

**读法**：我们选的 LangGraph 属于第三格。这意味着 **O / V / G 三层没有人为我们兜底，必须自建**。选型报告 §3.4 的生态分布数据（138 个开源项目中 L 层 47 个、C 层仅 9 个、O 层 15 个、G 层 14 个）印证了这一点：编排层最商品化、最不构成本项目壁垒；壁垒在 C（纵向个性化记忆）与 G（安全治理）。

| # | 挑战 | 关键数据 | 对 PRD 场景的意义 |
|---|---|---|---|

## 1.7 六元组自检表（本项目现状）

| 层 | 现状 | 差距 |
|---|---|---|
| **E** 执行循环 | `companion/engine.py` 的 `respond()` 主循环 + 时长/沉默控制 | 未开放代码执行，暂无沙箱需求 |
| **T** 工具注册表 | 危机干预（热线/通知人工）、量表计分 | 无注册表抽象；工具描述待规范化 |

| **S** 状态存储 | `risk_flag` / `scale_score` / `session` 表 | ⚠ 需显式区分"S 事实"与"C 视图" |

| **O** 可观测 | 仅 `audit_trace`，无成本/延迟面板 | 🟡 缺统一 trace 与延迟监控 |
| **G** 治理 | 风险词表 + 审核台 | 🟡 缺标准化生命周期钩子与不变量断言 |

# 第二章 基于 PRD v1.0 的框架选型与能力映射

## 2.1 先厘清：PRD 场景与选型报告假设的是两个产品

这是本章最重要的判断，直接决定选型结论。

| 维度 | 选型报告假设（长期陪伴） | **PRD v1.0（单次会话）** |
|---|---|---|
| 会话时长 | 无限、跨天、跨会话 | **≤ 5 分钟，单次** |
| 轮次 | 多轮、可持续数天 | **3-4 轮** |
| 输入模态 | 视频 + 自述 + 量表 + 对话 | **视频 + 语音（实时）** |
| 跨会话记忆 | ⭐ 核心差异化（纵向个性化） | **PRD §10 明确列为二期** |
| 量表 | PHQ-9/GAD-7 时序趋势 | **不涉及** |
| 输出 | 对话 + 风险评估 | **Tier1/2/3 三层报告** |
| 延迟要求 | 未明确 | **< 2 秒（PRD §7）** |
| 时间控制 | 无 | ⭐ **时长控制器 + 沉默检测（PRD 补齐 §7.1）** |
| 风险分级 | none/low/moderate/high/imminent（5 级） | **none/watch/high（3 级）** |

**结论**：选型报告推荐 LangGraph 的五条理由（见 §5.1）中，在 PRD 场景下——

| 原理由 | PRD 场景下是否仍成立 |
|---|---|
| 流程是确定性状态机 | ✅ **成立，且更强**（5 分钟会话的相位推进、超时收尾是硬状态机） |
| 必须能中途挂起等人工 | ✅ **成立**（high 级中断报告流程） |
| **必须可回放审计** | ⚠️ **弱化** —— 单次会话、无跨会话状态，时间旅行价值大幅下降 |
| 需要精确控制上下文注入 | ⚠️ **弱化** —— 3-4 轮，上下文远未触及窗口上限 |
| **并行多模态证据处理** | ❌ **不成立** —— 无跨会话多模态检索需求 |

也就是说：**LangGraph 在 PRD 场景下仍是最优解，但支撑它的理由只剩两条半**。这直接影响下面 §2.3 的"瘦身"方案。

## 2.2 候选框架针对 PRD 场景重新评估

评分维度按 PRD 的实际约束设定（5 分制）：

| 框架 | 状态机/相位控制 | 硬中断 | 实时多模态 | 延迟开销 | 团队存量 | 综合 |
|---|---|---|---|---|---|---|
| **LangGraph** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐（需自建） | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | **推荐** |
| **Google ADK** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐（原生 + bidi-streaming） | ⭐⭐⭐⭐⭐ | ⭐（无） | **条件性推荐**（见 §2.3.2） |
| **OpenAI Agents SDK** | ⭐⭐ | ⭐⭐⭐（Guardrails 原生） | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐ | 不推荐 |
| **LlamaIndex Workflows** | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐（多模态索引强） | ⭐⭐⭐ | ⭐ | 不推荐（PRD 无 RAG 需求） |
| **自研状态机** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐（全自建） | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | 备选（见 §2.3.3） |

**逐条说明**

- **LangGraph**：相位推进、超时边、风险跳转、模态降级都是状态机问题，这些是它的强项。缺点是多模态与实时流式需自建 —— 但 PRD 的多模态是**感知层外置**（§2.4 E 层），本来就不该由编排框架承担。
- **Google ADK**：唯一原生支持 video/audio 输入与 `LiveRequestQueue` 双向流的框架。**若 PRD 要做"边说边出字"的实时语音体验，这是 LangGraph 结构性缺失的能力**。代价是 Gemini 云绑定。
- **OpenAI Agents SDK**：Guardrails 原语对风险场景有吸引力，但状态机能力弱，撑不起 5 分钟相位控制。
- **LlamaIndex**：强在多模态索引与跨会话检索，PRD 单次会话用不上。
- **自研**：PRD 的状态机其实很小（5 个相位 × 3 个跳转），自研确实可行且延迟最优；但要自建审计与 HITL，得不偿失。

## 2.3 推荐结论

### 2.3.1 主推荐：LangGraph，按 PRD 场景做三处瘦身

| # | 瘦身项 | 理由 |
|---|---|---|
| 1 | **checkpointer 改为 `MemorySaver`**，仅 high/watch 会话落盘 | 单次会话无跨进程恢复需求；sqlite 每个 super-step 写盘在 <2s 预算下是纯开销。审计靠 `audit_trace` + `risk_flag` 表，不靠 checkpointer |
| 2 | **移除长期记忆分支** | PRD §10 明确列为二期。架构上保留 `memory_writer` 节点位，但默认 no-op |
| 3 | **风险检测与生成合并为一次结构化调用** | PRD 无跨会话并行需求，并行分支带来的复杂度收益为负；合并可省 2-4s（选型报告 §5 已指出这是延迟优化第一优先级） |

> ⚠ **第 3 点的安全边界**：合并的是「情绪评估 + 风险判定」两次**评估**调用，**不是**把风险判定与共情生成合并。风险检测与对话生成的**架构解耦**必须保留 —— 这是选型报告 §8.1 的硬原则。当前 `backend/graph.py` 的 `context_builder` 节点已按此实现（一次 `TurnAssessment` 同时产出情绪与风险），可直接继承。

### 2.3.2 条件性评估 ADK 的触发条件

**只在一种情况下值得做 POC**：PRD §7 的 <2s 若要按"实时边说边出字"理解（而非"录完一段再回复"），则需要双向流式管道。此时：

- LangGraph 只是编排层，**流式语音必须自建**（SSE/WebSocket + 流式 ASR + 流式 LLM）
- ADK 原生提供 `LiveRequestQueue` + bidi-streaming

**建议先与产品确认 PRD §7 的 <2s 到底指什么**（见 §2.7 延迟预算）。若确认是"完整生成 <2s"，无论哪个框架都做不到，应回到产品侧重新评审指标。

### 2.3.3 保留的后路

若实测发现 LangGraph 开销不可接受，降级路径是**自研相位状态机**（约 200 行），保留 `audit_trace` 与 `risk_flag` 落库即可。选型报告 §12 风险 3 已要求"编排层与记忆层解耦"，当前 `storage.py` 已独立，切换成本可控。

## 2.7 延迟预算拆解：<2s 是否可达

**结论：以当前模型配置不可达，且瓶颈不在框架。**

| 阶段 | PRD 目标 | 当前实测 | 主要优化手段 |
|---|---|---|---|
| ASR 转写 | 0.5s | ~1-2s（whisper small，非流式） | 流式 ASR；`small`→`base`/`tiny`（中文精度需评估） |
| 声学特征 | 0.1s | <0.1s（本地 numpy） | — 已达标 |
| 面部特征 | 0.2s | 端侧实时 | — 已达标 |
| 多模态融合 | 0.05s | <0.05s（规则） | — 已达标 |
| **风险检测** | 0.3s | **2-4s**（单独一次 LLM 调用） | ⭐ 与情绪评估合并为一次结构化调用（省 2-4s） |
| **生成回复** | 1.0s | **6-10s**（vLLM `kaiwu-llm-model`） | ⭐ 换 7-14B 小模型；流式首字优先 |
| 网络往返 | 0.3s | — | — |
| **合计** | **< 2s** | **~10s（实测）** | 需压缩 5 倍 |

**优化优先级（按性价比）**

1. **合并风险检测与情绪评估**（省 2-4s，零质量损失）— `graph.py` 已实现 `TurnAssessment` 合并，PRD 场景直接继承
2. **换更小模型**（当前实测 10s，7-14B + 针对性微调可望降到 2-3s）
3. **流式首字优先**：先返回一句共情话术（"嗯，我在听…"）占位，感知延迟可压到 1s 内
4. ASR 降级或流式化
5. 感知并行化（ASR 与面部聚合可并行）

> **需要产品侧确认**：在当下模型能力下「完整生成 < 2s」很难达到。更现实的目标是「**首字 < 1.5s + 完整 < 5s**」。这一条已同步记入 `docs/miniprogram_plan.md` §5。

| # | 红线 | PRD 场景的具体含义 |
|---|---|---|

# 第三章 冷启动用户的画像建模与主动提问

> 参考：`docs/user-centric_proactive agent 调研.docx`（下称 **proactive 调研**）

## 3.1 冷启动问题的实质

PRD 场景的冷启动是**极端信息稀缺**：

| 约束 | 数值 |
|---|---|
| 可用时长 | ≤ 5 分钟 |
| 用户说话轮次 | 3-4 轮 |
| 历史数据 | **零**（首次使用） |
| 需要产出 | 主导情绪 + 状态描述 + 次情绪 + 自助建议 + 风险判定 |

同时存在**三个相互冲突的张力**：

### 张力一：主动提问 vs 用户负担

要个性化就必须获取信息，但在 5 分钟内提问是**昂贵**的（每问一次就少一轮倾听）。PRD §6.2 明确要求"避免连续追问造成压迫感""追问深度不超过两层"。

proactive 调研中的 **BAO**（*Pushing Forward Pareto Frontiers of Proactive Agents*）正是把这件事建模为**多目标优化**：最大化任务性能 vs 最小化用户参与度，寻找帕累托前沿。它刻画的两种核心行为直接对应本项目：

- **回顾性推理**（Retrospective Reasoning）：整合与修正历史信息（含记忆管理与假设修正）
- **前瞻性规划**（Prospective Planning）：当前推理与未来动作结合（含动态调度与**策略性查询**）

BAO 的 RL 惩罚项也直接可用：**信息搜寻正则化**——惩罚"未从环境获得新信息却反复向用户发问"的冗余行为。

### 张力二：冷启动无先验 vs 个性化要求

没有历史就无法个性化。proactive 调研中的 **PAHF**（*Learning Personalized Agents from Human Feedback*）指出静态方法（Offline 数据集训练、外挂预设画像）的三个失败：

1. 无法在没有历史数据的情况下适应新用户 ← **正是冷启动**
2. 无法从实时纠正性反馈中学习
3. **偏好漂移**时无法调整

PAHF 的解法是**显式 per-user memory + 双反馈通道**（行动前预问 / 行动后纠正），并设计了四阶段评估协议：

| 阶段 | 内容 | 本项目对应 |
|---|---|---|
| 1 初始学习 | 从空记忆开始，利用交互反馈从零学习 | 首次会话（冷启动） |
| 2 初始个性化测试 | 无反馈下，用阶段 1 记忆在新场景决策 | 第二次会话 |
| **3 漂移适应** | 重放旧场景但**替换为用户已演变的画像**，使旧记忆产生"自信的错误" | ⭐ 用户生活境遇变化后 |
| 4 适应后测试 | 验证是否已覆盖过时记忆 | 后续会话 |

> 阶段 3 在心理健康场景尤其危险：系统记住"用户社会支持良好"，但用户最近刚离婚/失业/丧亲。**旧画像会自信地错**。这要求画像必须有**来源追溯 + 时间衰减 + 矛盾标记**。

### 张力三：满意度 ≠ 临床正确性

通用 proactive agent 用"任务成功率 + 用户满意度"优化。但心理健康场景，**用户满意度不是充分指标**——一个让用户舒服但漏掉风险信号的 Agent 是失败的。这引出 §3.6 的三条硬约束。

## 3.2 相关工作梳理

### 3.2.1 主动协作与信息增益

| 工作 | 核心机制 | 对冷启动提问的可用性 |
|---|---|---|
| **CollabLLM** | 多轮感知奖励（MR）+ 协作模拟：LLM 扮演带隐性目标的用户模拟器，前向采样推演未来对话 | ⭐ **用户模拟器 + 前向采样**可直接用于"这一步提问是否值得"的离线评估。真实用户研究：满意度 +17.6%，任务耗时 −10.4% |
| **InfoPO** | **轮次级反事实信息增益**：比较「含真实用户反馈的历史」与「反馈被掩码的历史」下 agent 下一动作分布的差异 | ⭐⭐ **最有价值**。给出了"这一问值多少"的可计算定义（见 §3.4） |
| **ITPO** | 隐式轮次级过程奖励：从稀疏结果信号推导细粒度 turn-wise 奖励，无需人工标注或蒙特卡洛采样 | ⭐ 解决"5 分钟会话只有最终结果可用"的信用分配问题 |

**InfoPO 的信息增益形式化**：

\[
\text{IG}_t = D_{KL}\Big(\pi(a_{t+1} \mid h_t, u_t) \;\|\; \pi(a_{t+1} \mid h_t, [\text{MASK}])\Big)
\]

即：拿到用户第 \(t\) 轮的反馈后，agent 下一步动作分布改变了多少。改变越大 = 该反馈信息量越大 = 这一问越值得。

### 3.2.2 交互负担的多目标权衡

| 工作 | 核心机制 |
|---|---|
| **BAO** | 帕累托前沿（任务性能 vs 用户参与度）；行为增强（SFT 注入规划/回顾行为）+ 行为正则化（RL 惩罚冗余交互与过度思考）。指标 `Pass@U-k`（最多 k 次用户交互下的通过率）、`UR` 用户参与率 |
| **MUA-RL** | 多轮用户交互 agent RL；**SFT 冷启动初始化**被证明是解锁初始交互能力的关键 |

### 3.2.3 持续个性化与偏好漂移

**PAHF**：显式 per-user memory + 双反馈通道（Pre-action / Post-action）+ 偏好漂移基准（逻辑反转 Logical Inversion、随机重采样 Stochastic Resampling）。指标：成功率 SR、反馈频率 FF、**平均累积个性化误差 ACPE**。

### 3.2.4 无梯度记忆进化

**PRIME**（*Training Free Proactive Reasoning via Iterative Memory Evolution*）是本章对本项目**推荐度最高**的工作。

- **不做梯度更新**，把能力提升视为对**记忆库 \(\mathcal{M}\)** 的优化而非对策略参数 \(\theta\) 的优化
- 记忆结构化表示：\(m = (m_{core}, m_{stage}, m_{cond}, m_{zone})\)，分三个语义区：**黄金区**（成功策略）/ **警告区**（失败模式）/ **偏好区**（用户行为模式）
- 三阶段：**探索 → 提炼**（用多轮信用分配识别关键轮次）**→ 进化**
- 四种进化算子：

| 算子 | 触发条件 | 概率 | 映射到本项目 |
|---|---|---|---|
| **变异** | 记忆被检索调用但导致次优结果 | 0.10 | 画像被引用却判断失误 → 修正措辞/适用条件 |
| **泛化** | 在多个环境均成功（成功率 ≥0.7） | 0.05 | 「和领导吵架」→「对权威评价敏感」 |
| **交叉** | 两条记忆情境重叠但策略互补 | 0.02 | 多条事实合成一个模式 |
| **修剪** | 周期性维护（每 2 迭代） | — | 移除过时/低价值条目 |

**为什么 PRIME 对本场景优于 RL**：

| 维度 | RL（InfoPO/BAO/PAHF） | PRIME（无梯度） |
|---|---|---|
| 计算成本 | 多 GPU 数天 | 仅前向传播 |
| **可解释性** | 参数改进不可解释 | ⭐ 记忆是文本，**可人工审阅** |
| **可修正性** | 需重训 | ⭐ 直接编辑/删除一条记忆 |
| 跨模型迁移 | 绑定参数 | ⭐ 记忆库可跨架构迁移 |
| 合规审计 | ❌ 黑箱 | ⭐ 事故复盘可追溯 |

在心理健康这种高责任场景，**"可解释、可审计、可人工修正"的价值高于"端到端最优"**。发生误判时，我们需要能回答"系统当时依据什么做出了这个判断"——记忆库可以，RL 参数不行。

### 3.2.5 奖励设计的陷阱（必读）

**Multi-Turn RL with Iterative Reward Calibration**（IRC）给出了一个反直觉的实证结果：

> **即使是基于合理直觉设计的密集每轮奖励，也会因为奖励区分度与优势计算方向不一致（优势错位），导致模型性能产生高达 14 个百分点的灾难性下降。**

解法是 **IRC（迭代奖励校准）**：不靠直觉分配奖励，而是通过闭环流程——收集表现数据 → 测量每个奖励层级与最终成功的**经验相关性**（点二列相关）→ 检查组归一化后的优势方向是否符合预期。例如分析发现"只读工具调用几乎没有区分度，应获零奖励"。

**对本项目的直接警示**：如果给"主动提问"设正奖励，很可能训练出**疯狂追问**的 Agent。任何奖励项在上线前必须做经验区分度分析。

### 3.2.6 用户模拟器

proactive 调研列出：`Non-Collaborative User Simulators`、`Mind the Sim2Real Gap`、`Pare: Proactive Agent Research Environment`、`Consistently Simulating Human Personas with Multi-Turn RL`、`User Simulator-Guided Multi-Turn Preference Optimization`。

**通用模拟器对心理场景不够**，见 §3.7。

| 工作 | 解决的问题 | 本项目可用性 | 阶段 |
|---|---|---|---|
| CollabLLM | 主动澄清 + 用户模拟 + 前向采样 | 高（模拟器 + 离线评估） | 1-2 |

## 3.3 用户建模三层 Schema

对齐 proactive 调研「方案」部分的三层划分，并落到 PRD 场景：

| 层 | 字段 | 来源 | 更新频率 | **冷启动默认值** | 置信度 |
|---|---|---|---|---|---|
| **会话目标** | 本次想聊什么（可跳过） | 开场轻量询问 / 用户主动提及 | 每会话 | **空**（不强制问，避免浪费轮次） | — |
| **瞬时状态**<br>（隐式） | 情绪（valence/arousal + 类别）<br>耐心、信任、困惑、被打断程度 | 每轮多模态融合 + 交互行为推断 | **每轮** | 面部/声学基线（当轮即可得） | 中（有模态支撑） |
| **稳定画像**<br>（长期） | 人格特质、应对风格、社会支持、**触发源**、沟通偏好、风险史 | 事实抽取 + 用户显式反馈 | 跨会话 | ⭐ **先验问卷**（见下） | 低 → 随会话累积升高 |

### 3.3.1 冷启动的"温启动"改造

**核心思路：把能离线收集的，绝不留给 5 分钟会话。**

首次使用时用一道**极短的显式问卷**（30 秒，可跳过）建立种子画像，把冷启动变成温启动：

| 题目 | 画像字段 | 为什么值这个时间 |
|---|---|---|
| 最近主要想聊聊哪方面？（工作/学业/关系/健康/其他） | 触发源 | **直接决定开场问题的方向**，省掉一轮探测 |
| 你更希望我：（A）多听少说（B）多问细节（C）给具体建议 | 沟通偏好 | 直接决定提问密度，**避免冒犯** |
| 过去两周整体状态？（1-5） | 情绪基线 | 提供"相对变化"的参照系 |

> 这与 PAHF 的"Pre-action 反馈通道"同源：**行动前先问**，比行动后纠正便宜得多。

### 3.3.2 画像的"防漂移"字段（PAHF 阶段 3 的工程解）

每条画像事实必须携带：

| 字段 | 作用 |
|---|---|
| `source` | 来源追溯（哪次会话、哪种抽取方式） |
| `extracted_at` | 时间衰减的依据：置信度随时间的指数衰减 |
| `confidence` | 冷启动期低 → 在融合/决策中**降权** |
| `contradicted_by` | 新证据与旧事实冲突时**不静默覆盖**，标记待消解（由用户或后续会话确认） |
| `user_editable` | 用户可查看、可删除（合规刚需，PRD §8） |

> **与 PRD 的呼应**：PRD §6.3.3 要求"权重可根据模态置信度动态调整（如面部遮挡/低光时降低视觉权重）"。这里把同一原则**扩展到画像置信度**——冷启动期画像置信度低，就降低其在判断中的权重，宁可多依赖当轮的模态证据。

## 3.4 主动提问决策框架

### 3.4.1 四个问题

| 问题 | 判据 |
|---|---|
| **何时问** | 信息增益 > 阈值 **且** 轮次预算未耗尽 **且** 用户瞬时状态允许 |
| **问什么** | 按 \(\text{IG}(q) - \lambda \cdot \text{Cost}(q)\) 排序取最大 |
| **怎么问** | 结合瞬时状态调整语气与深度（用户疲惫/困惑时降密度） |
| **何时停** | ① \(\max_q \text{IG}(q) < \tau\) ② 轮次耗尽 ③ 进入收尾区 ④ **⛔ 风险触发（硬约束）** |

### 3.4.2 决策公式

\[
q^* = \arg\max_{q \in \mathcal{Q}}\ \Big[\ \underbrace{\text{IG}(q)}_{\text{信息增益}}
- \underbrace{\lambda \cdot \text{Cost}(q)}_{\text{轮次成本}}
- \underbrace{\mu \cdot \text{Burden}(u_{t})}_{\text{用户负担}}\ \Big]
\]

其中：

- \(\text{IG}(q)\)：提问 \(q\) 后对目标变量（情绪判定 / 风险等级）不确定性的减少量
- \(\text{Cost}(q)\)：轮次成本。PRD 预算仅 3-4 轮，每问一次成本极高
- \(\text{Burden}(u_t)\)：基于**瞬时状态**的负担惩罚。用户疲惫/困惑/不耐烦时上调

### 3.4.3 \(\text{IG}(q)\) 的在线可计算近似

InfoPO 的严格定义需要对比两个分布，在线算太重。三个可用的近似（按成本递增）：

**① 熵差法（推荐，纯在线）**

\[
\text{IG}(q) \approx H(Y \mid h_t) - \mathbb{E}_{x \sim q}\big[H(Y \mid h_t, x)\big]
\]

实现：让 LLM 输出当前情绪分布 → 算熵 \(H(Y|h_t)\)；再让 LLM 自评"若知道 \(x\)，判断会改变多少"（0-1）→ 近似第二项。

**② LLM 自评法（最轻）**

> 给定当前已知信息，"如果再知道 \(X\)，你对用户情绪状态/风险的判断会有多大改变？" 0-1 打分。

**③ 离线校准（最准）**

用 CollabLLM 的**前向采样 + 用户模拟器**离线跑，统计每个候选提问对最终判断准确率的边际贡献，固化为提问优先级表。

### 3.4.4 ⛔ 硬约束：风险触发时停止一切探索式提问

这是心理健康场景与通用 proactive agent 的**根本差异**：

```
if risk_level == 'high':
    # 信息增益再高也不许问
    # 不追问计划细节、不探索情绪成因
    # 立即：表达关心 → 给出热线 → 鼓励联系身边人 → 等待人工
    return CRISIS_PROTOCOL
```

**理由**：在危机语境下，追问"你是怎么计划的"不仅无益，还可能有害（PRD 补齐 §7.5.3 明确要求"不追问细节、不评价"）。信息增益在这里不是目标，**安全是**。

### 3.4.5 伪代码

```python
def decide_next_action(state, user_state, budget):
    # ① 硬约束优先：风险触发时立即停止探索
    if state.risk_level == 'high':
        return CRISIS_PROTOCOL

    # ② 时间/静默硬边界（PRD §7.1）—— 轮次不再是终止条件
    if state.elapsed >= HARD_LIMIT:
        return CLOSING

    if state.idle_sec >= IDLE_END_AT and state.idle_stage >= 1:
        return CLOSING                        # 静默 90s：确认过仍无回复

    if state.elapsed >= WRAP_UP_AT:          # 4:00 收尾提醒
        return wrap_up_transition()

    # ③ 静默阶梯（PRD §7.1）
    gap = state.seconds_since_user()
    if gap >= IDLE_CONFIRM_AT: return IDLE_CONFIRM   # 60s：「这次先聊到这里吗」
    if gap >= 8:               return SILENCE_PROMPT # 8s：「不着急，你可以慢慢说」

    # ④ 主动提问决策
    candidates = generate_questions(state, user_state)
    scored = [
        (ig(q) - LAMBDA * cost(q) - MU * burden(user_state), q)
        for q in candidates
    ]
    best_score, best_q = max(scored)

    if best_score < TAU_IG:                  # 没有高价值问题
        return empathetic_response(state)     # 改为共情回应，不硬凑提问
    if state.followup_depth >= 2:            # PRD: 追问 ≤2 层
        return open_new_topic() or CLOSING
    return ask(best_q)
```

## 3.5 冷启动三阶段路线

| 阶段 | 数据条件 | 方法 | 风险 |
|---|---|---|---|
| **阶段 0 · 温启动** | 零数据 | 先验问卷 + 规则风险通道 + LLM few-shot + **信息增益启发式**（LLM 自评） | 低。重点是**不犯错**，而非个性化 |
| **阶段 1 · 无梯度记忆进化** | 有真实会话日志（数百条） | **PRIME 式**：从轨迹提炼记忆 → 四算子进化 → 检索注入 | 低。可解释、可人工修正、可回滚 |
| **阶段 2 · 受约束的 RL** | 有专业标注集（数千条，含风险分级） | InfoPO/ITPO 信用分配 + BAO 多目标约束 + **IRC 奖励校准** | ⚠ 高。必须在阶段 1 稳定后启动 |

**为什么这个顺序**：

1. **IRC 的警告**——直觉奖励会导致 14pp 的灾难性下降。没有经验数据就做 RL，等于必踩这个坑。
2. **MUA-RL 的发现**——SFT 冷启动是解锁初始交互能力的前提。阶段 1 的记忆库正好充当这个"冷启动"。
3. **合规优先**——阶段 1 的记忆库可审计、可人工编辑，更容易通过伦理审查；阶段 2 的黑箱参数不行。

## 3.6 心理健康场景对 RL 的三条硬约束

通用 proactive agent 的优化目标是"任务成功 + 用户满意"。本项目不能直接套用：

### 约束一：安全是约束，不是奖励项

不要把"不输出有害内容"放进奖励函数做加权。应做成**硬约束**：约束 RL（CMDP）或后处理护栏。

\[
\max_\pi\ \mathbb{E}[R_{\text{quality}}] \quad \text{s.t.} \quad \mathbb{E}[C_{\text{safety}}] \leq \kappa
\]

理由：奖励加权意味着"足够高的质量分可以换取一定的安全风险"，这在心理健康场景不可接受。

### 约束二：用户满意度 ≠ 临床正确性

满意度是**必要不充分**指标。一个让用户舒服但漏掉风险信号的 Agent 通过满意度评测，却是失败的。

必须有的配套：
- 专业标注的离线评测集（含隐晦表达、反讽、方言、**模态不一致**等困难样本）
- **风险召回率作为红线指标**（选型报告 §10：Recall ≥ 0.95）
- 每次 prompt/模型/harness 变更都跑回归（选型报告 §12 风险 6）

### 约束三：可解释、可审计优先于端到端最优

这是推荐 **PRIME 优先于 RL** 的根本原因。事故复盘时我们必须能回答"系统当时依据什么做出这个判断"。记忆库可以，RL 参数不行。

## 3.7 用户模拟器设计

### 3.7.1 为什么通用模拟器不够

UserVille / UserRL / τ²-Bench 等环境的用户，缺少心理场景的**关键维度**：

| 缺失维度 | 为什么关键 |
|---|---|
| **情绪状态机** | 通用模拟器的"偏好"是静态的；情绪随对话演化（被理解 → 舒缓；被误解 → 关闭） |
| **人格/依恋风格** | 决定信任建立速度，直接影响愿意透露多少 |
| **⭐ 掩饰倾向** | **心理场景独有且最难模拟**：嘴上说"我挺好的"，实际低落。这是 PRD §6.3.3 明确要检测的模态不一致 |
| **生活境遇/触发源** | 决定话题敏感度 |
| **漂移** | 跨会话状态变化（失业/分手/丧亲），PAHF 阶段 3 |

### 3.7.2 模拟器的最小扩展

在通用模拟器上叠加：

```
UserProfile（模拟用）
├── 情绪状态：valence/arousal + 类别，带演化规则
├── 掩饰倾向 α ∈ [0,1]：决定"说出口的内容"与"真实状态"的偏离度
├── 人格/依恋风格：影响信任建立速率与自我暴露深度
├── 生活境遇：触发源集合
└── 漂移规则：跨会话的状态转移概率
```

**关键设计**：掩饰倾向 \(\alpha\) 让模拟器产出**模态不一致**的样本（文本正面 + 声学/面部负面），这是训练与评估多模态融合的必需数据。

### 3.7.3 人工标注兜底

模拟器**不能替代专业标注**，尤其是风险分级：

- 模拟器可以批量造"多样性"，但造不出"临床正确性"
- 风险分级（C-SSRS 维度）必须由**精神卫生专业人员**标注
- 选型报告 §10 已明确："必须建立含专业标注的离线评测集"
- PRD §10 也要求："风险信号识别的准确率与话术，建议引入心理健康领域专家参与评审"

## 3.8 评估方案

| 维度 | 指标 | 目标 | 阶段 |
|---|---|---|---|
| **冷启动画像质量** | 首次会话后画像与后续会话的一致性 | 基线待测 | 0-1 |
| **主动提问有效性** | 提问的信息增益（离线用前向采样测） | 高于随机提问基线 | 0-2 |
| | `Pass@U-k`（最多 k 次用户交互下的判断准确率） | 随 k 增长迅速饱和 | 1-2 |
| **交互负担** | 用户参与率 UR、追问深度、会话中断率 | UR 越低越好；追问 ≤2 层 | 0-2 |
| **情绪识别** | 与专业标注的一致性（加权 Kappa）、分类 F1 | 待测（PRD 未定目标值） | 0-2 |
| **风险检测** | **召回率优先**，其次 Precision | **Recall ≥ 0.95**，漏报为红线 | 0-2 |
| **画像漂移适应** | PAHF 的 ACPE（平均累积个性化误差） | 阶段 3 vs 阶段 4 显著下降 | 1-2 |
| **记忆库质量** | 检索命中率、过时条目占比、修剪后性能保持 | — | 1 |
| **系统** | 单轮延迟、危机响应时延 | 见 §2.7 | 0 |

> **评估对象应是完整 trace，不只是最终结果**（选型报告 §3.7）。除结果正确性外，还要评估**路径合理性**（是否漏跑任一通道、是否走了危机协议、是否靠重试刷过）与**评估器可信度**（多标注员一致性、困难样本覆盖率）。单一通过率会掩盖"走了不安全路径碰巧做对"这类缺陷。

## 3.9 落地清单

**立即可做（阶段 0）**
- [ ] 先验问卷三题（触发源 / 沟通偏好 / 状态自评），写入 `user_profile`
- [ ] 画像事实表补齐 `source` / `extracted_at` / `confidence` / `contradicted_by` / `user_editable`
- [ ] 主动提问的信息增益启发式（LLM 自评版）接入 `engine._generate_reply()`
- [ ] 轮次/追问深度/时间预算三者的联合硬约束（PRD §7.1 + §6.2）
- [ ] 风险触发时禁止一切探索式提问的断言

**阶段 1（有数据后）**
- [ ] 轨迹提炼流水线：用信用分配识别关键轮次 → LLM 抽取结构化记忆
- [ ] 记忆库三区（黄金/警告/偏好）+ 四算子（变异/泛化/交叉/修剪）

- [ ] 用户模拟器：叠加情绪状态机 + 掩饰倾向 α + 漂移规则

**阶段 2（有专业标注后）**
