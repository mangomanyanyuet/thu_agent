# 主流 Agent 框架调研报告
## —— 兼「个性化多模态心理学 Agent」技术选型建议

- **调研时间**：2026-08
- **更新记录**：2026-08-29 —— 新增第 3 章「Agent Harness Engineering」综述（ETCLOVG 七层框架），据此补充 §10 评估方案与 §12 开放问题
- **目标场景**：一个心理健康 App，每天采集用户的 ① 基础信息 ② 视频（面部/语音） ③ 一段自述文本 ④ 心理评测问卷；用户同时与 Agent 进行多轮对话。Agent 需要：
  1. 识别情绪与心理状态（个性化、纵向追踪）
  2. 识别危险性（自杀/自伤倾向）并**分级**
  3. 轻度 → CBT 疗愈式对话引导；重度 → 危机干预（求助热线、人工介入）
- **本报告解决四个问题**：
  1. 现在最火的 Agent 框架有哪些？
  2. 它们怎么处理「上下文 / 历史信息 / 记忆」？
  3. 哪个（组合）最适合本项目？
  4. **模型之外，还需要补齐哪些系统层，才能真正可靠地上生产？（§3）**

## 0. 结论先行（TL;DR）

| 层次 | 推荐选型 | 一句话理由 |
|---|---|---|
| **编排层** | **LangGraph** | 心理评估天然是「状态机 + 条件分支 + 人在回路」，LangGraph 是唯一把这三件事做成一等公民的框架，且 checkpointer 让每次评估**可回放、可审计**（医疗合规刚需） |
| **多模态检索层** | **LlamaIndex**（多模态索引 + Memory Blocks） | 视频抽帧/语音/文本统一索引最成熟；`FactExtractionMemoryBlock` 能把对话自动沉淀为「用户事实」 |
| **长期记忆层** | **mem0 / Zep** + 自建 `UserProfile` 表 | 跨天个性化的关键：不是把历史全塞进上下文，而是抽取成事实 + 检索式注入 |
| **结构化层** | **PostgreSQL**（量表时序 + `risk_flags`） | 量表趋势、风险事件必须是强结构化、可查询、不可被摘要丢失的 |
| **安全层** | **独立的风险检测通道**（与对话生成解耦） + 规则/模型双召回 + HITL | 学术界 2026 年的共识做法（见 §8.1），不能让「共情式对话模型」同时兼任「风险判定者」 |
| **系统观（Harness）** | 按 **ETCLOVG 七层**逐层自检（见 §3） | 编排层（L）已商品化，**不构成壁垒**；壁垒在 C（纵向个性化记忆）与 G（安全治理），**短板在 V（轨迹评估）与 O（可观测）** |

> 若团队**全线使用 Gemini 且希望最少自研**：可用 **Google ADK** 一套替代 LangGraph+LlamaIndex（原生 video 输入 + 双向流 + MemoryService + Context Compaction），代价是云厂商绑定。
> 若团队是 **Java/.NET 技术栈**：用 **Microsoft Agent Framework (MAF)** 或 **Spring AI Alibaba**。

## 1. 2026 年 Agent 框架全景

经过 2024「元年」、2025「爆发」，2026 年进入**格局收敛期**：通用编排框架头部化，同时分化出「记忆层」「协议层」两个独立赛道。

### 1.1 第一梯队：通用编排框架

| 框架 | 语言 | 核心哲学 | 生产成熟度 | 适合场景 |
|---|---|---|---|---|
| **LangGraph**（LangChain） | Python / TS | **显式状态图**：节点=步骤，边=状态流转 | ★★★★★ | 长流程、需精确控制、需审计/回滚、人在回路 |
| **Microsoft Agent Framework (MAF)** | Python / .NET | **AutoGen 的 Agent 抽象 + Semantic Kernel 的插件/上下文增强**合并体 | ★★★★☆ | 企业级、Azure 生态、已有 SK 存量 |
| **CrewAI** | Python | **角色驱动团队**：Crew → Agent → Task | ★★★★☆ | 业务人员可读、任务分工明确、快速交付 |
| **LlamaIndex Workflows** | Python / TS | **事件驱动**，文档/RAG 优先 | ★★★★☆ | 知识密集、多模态检索、需要 RAG 深度定制 |
| **Google ADK** | Python / Java | **Session/State/Memory 三元 + A2A** | ★★★★☆ | Gemini 生态、实时多模态、Vertex 部署 |
| **OpenAI Agents SDK** | Python / TS | **极简原语**：Agent / Handoff / Guardrail / Session | ★★★★☆ | 快速起步、OpenAI 生态、轻量 Agent |
| **Claude Agent SDK** | Python / TS | 长任务 + 工具使用 + 自动上下文压缩 | ★★★★☆ | 编码类/长时任务 Agent |
| **Pydantic AI** | Python | **类型安全优先**，输出即 Pydantic 模型 | ★★★★☆ | 强结构化输出（量表打分、风险分级） |
| **Mastra** | TypeScript | TS 原生全栈 Agent | ★★★☆☆ | 前端团队、Node 服务 |
| **Agno**（原 Phidata） | Python | 极轻量、低内存 | ★★★☆☆ | 快速原型、边缘部署 |
| **Dify / Coze / n8n** | 低代码 | 可视化编排 | ★★★★☆ | 运营侧编排、非算法同学参与 |

> 注：Star 数与「热度排名」在不同统计口径下差异较大（有报告称 LangGraph 占 40%+ 生产份额，也有报告把 CrewAI/AutoGen 排在前），**不建议以 Star 数作为选型依据**，应以「上下文/状态能力是否匹配业务」为准 —— 这正是下一章的重点。

### 1.2 第二梯队：记忆 / 上下文专用层（2026 年新变量）

这类项目**不是**编排框架，而是可插到任意框架下的「记忆中间件」，对本项目极其重要：

| 项目 | 定位 | 关键能力 |
|---|---|---|
| **mem0** | 自动记忆抽取层 | 从对话中抽取事实、**冲突消解**（新信息覆盖旧信息）、图记忆、按用户/会话/Agent 三级作用域 |
| **Zep / Graphiti** | 时序知识图谱记忆 | 把历史构建成**带时间边的知识图谱**，可回答「他上个月心情如何变化」 |
| **Letta**（原 MemGPT） | 有状态 Agent 运行时 | 分层记忆（core / archival / recall），Agent 自主管理自己的记忆 |
| **Cognee / Memobase** | 记忆管道 | ETL 式记忆构建 |

### 1.3 第三梯队：协议标准

- **MCP（Model Context Protocol）**：工具/数据源接入的事实标准，上述框架基本全支持。
- **A2A（Agent2Agent）**：Agent 间通信协议（Google 主导），跨框架协作用。
- **AG-UI**：Agent 与前端 UI 的流式交互协议（对 App 端实时展示情绪状态有用）。

## 2. 【核心】各框架的上下文 / 历史信息处理机制

这是本项目选型的决定性维度。心理 Agent 的上下文需求非常特殊：

- **单会话内**：多轮对话必须连贯，且**危险信号绝对不能因为上下文裁剪而丢失**
- **跨天/跨会话**：需要长期个性化（人格特质、既往风险史、触发事件、量表轨迹）
- **多模态**：视频/语音/量表证据要能被关联进上下文
- **可审计**：任何一次风险判定都要能追溯当时的完整上下文

### 2.1 逐框架拆解

#### LangGraph
- **短期上下文**：`State`（通常含 `MessagesState`），按 `thread_id` 组织；`add_messages` reducer 做消息合并/去重。
- **持久化**：原生 **Checkpointer**（`MemorySaver` / `SqliteSaver` / `PostgresSaver` / `AsyncPostgresSaver`）。每个 super-step 存一个 checkpoint → 支持 **时间旅行（回到任意历史状态）** 与 **状态分叉**。
- **长期记忆**：`BaseStore`（`InMemoryStore` / `PostgresStore`），支持命名空间 + 向量检索，官方定位为「跨 thread 的长期记忆」。
- **上下文裁剪/压缩**：**手动可控**。常用手段：
  - `trim_messages(strategy="last", max_tokens=...)` 保留最近 N token
  - 自定义 `summarize_node`：超阈值时把旧消息用 LLM 摘要，替换为一条 system summary
  - `RemoveMessage` 显式删除特定消息
- **人在回路**：`interrupt()` + `Command(resume=...)`，原生支持「挂起等人工审核」——**本项目高风险分支的关键能力**。
- **多模态**：消息 `content` 支持 list（text/image_url/audio），但多模态检索需自建。
- **评价**：可控性/可审计性最强，代价是记忆策略要自己写。

#### LlamaIndex Workflows
- **短期上下文**：`Context` 对象贯穿所有 step，`ctx.store.get/set` 存全局状态；事件驱动，天然异步/并行。
- **持久化**：`ctx.to_dict()` / `Context.from_dict()` 序列化落库，支持中断-恢复（HITL）。
- **长期记忆**：⭐ **`Memory` + Memory Blocks 组合**，是本项目最值得借鉴的设计：
  - `StaticMemoryBlock`：固定注入（如用户基线画像、安全 prompt）
  - `FactExtractionMemoryBlock`：**自动从对话抽取事实**并累积（如「用户提到与父亲关系紧张」）
  - `VectorMemoryBlock`：历史对话向量化，按当前 query 语义召回
  - 支持 `token_limit` + `chat_history_token_ratio`：短期窗口 + 长期块的 token 预算分配
- **多模态**：⭐ **最成熟**。`ImageNode` / `ImageDocument`、`MultiModalVectorStoreIndex`（文本与图像分别建索引联合检索）、视频抽帧 + ASR 后统一入库。
- **评价**：多模态 + 记忆能力最强，流程控制的显式性弱于 LangGraph。

#### Microsoft Agent Framework (MAF) / 原 AutoGen
- **短期上下文**：`AgentThread` 概念（合并后统一），消息历史随 thread 走；原 AutoGen 的 `ConversableAgent.chat_messages` + `max_consecutive_auto_reply` 控轮数。
- **持久化**：`thread` 可序列化；需自行选择存储后端。
- **长期记忆**：继承 SK 的 memory/plugin 体系；也常外接 mem0 / 向量库。
- **压缩**：消息 `transform` 机制（截断、过滤、摘要）；多 Agent 群聊场景下 token 增长快，需主动治理。
- **多模态**：支持多模态消息，但无专门抽象。
- **评价**：企业集成好，多 Agent 讨论（可用于「多评估者投票降低漏报」）；状态可控性中等。

#### CrewAI
- **内置三层记忆**（`memory=True` 即开）：
  - **Short-term**：当前执行的对话/上下文（RAG 存储）
  - **Long-term**：任务执行结果沉淀，默认落本地 SQLite，跨 run 可用
  - **Entity memory**：抽取实体（人、事、概念）→ 很适合做「用户画像」
  - 另有 `Contextual Memory` 把三者组合注入
- **压缩**：短期记忆超窗口自动 LLM 摘要。
- **评价**：记忆开箱即用是最大优点；但图/条件控制能力弱，**风险分级这种必须精确的分支逻辑不如 LangGraph 可靠**。

#### OpenAI Agents SDK
- **Sessions**：`SQLiteSession` / `OpenAIConversationsSession`，**自动**存取历史，开发者无需手动拼 messages；支持 `pop_item` 做「撤回上一轮」。
- **Guardrails**：输入/输出护栏（并行运行的小模型/规则），可在检测到高危输入时**立刻中断主流程** → 对本项目很关键。
- **Handoffs**：Agent 间转交，可在转交时裁剪上下文。
- **长期记忆 / 多模态索引**：无内置，需自建。
- **评价**：最快起步，安全护栏原语好；记忆深度不足。

#### Google ADK
- **三元结构**：`Session`（一次会话 + `events` 事件流）/ `State`（键值状态，支持 `user:` `app:` `temp:` 前缀作用域）/ `Memory`（跨会话长期记忆）。
- **持久化**：`InMemory` / `Database` / `VertexAiSessionService`。
- **长期记忆**：`MemoryService`（`InMemory` / `VertexAiRagMemoryService`），`add_session_to_memory()` 把会话沉淀入长期库，`load_memory` 工具检索。
- **压缩**：**Context Compaction**（较新特性）按 token 阈值自动压缩事件历史。
- **多模态**：⭐ **原生**。直接传 video/audio/image（Gemini 原生多模态）；`LiveRequestQueue` + bidi-streaming 支持**实时音视频对话**。
- **Callbacks**：`before_model_callback` 等钩子可在每次调 LLM 前强制注入/校验（可用于强制注入风险标记）。
- **评价**：如果全线 Gemini，是「多模态 + 记忆 + 实时」一体化程度最高的选择。

#### Claude Agent SDK / Pydantic AI / Agno（简述）
- **Claude Agent SDK**：内置**自动上下文压缩**（长任务时自动摘要旧上下文）、子 Agent 隔离上下文，适合长时任务。
- **Pydantic AI**：`message_history` 显式传递 + 输出强类型校验。**本项目建议用它（或 LangGraph 里的 structured output）来保证量表打分/风险分级的输出格式 100% 可解析**。
- **Agno**：轻量，自带 session storage + memory，适合原型。

### 2.3 上下文处理的三种范式（本质总结）

1. **全量重放型**（LangGraph checkpointer、ADK Session events）
   - 优点：忠实、可审计、可回滚
   - 缺点：token 成本随轮数线性增长
   - 必须搭配：滑动窗口 + 摘要节点
2. **事实抽取型**（mem0、LlamaIndex FactExtraction、CrewAI EntityMemory、Zep 图记忆）
   - 优点：token 成本近似常数，**长期个性化效果最好**
   - 缺点：抽取会丢信息，需要防止「关键信息被抽丢」
3. **自动压缩型**（ADK Compaction、Claude SDK auto-compact、CrewAI 摘要）
   - 优点：工程成本最低
   - 缺点：压缩策略不透明，**不适合承载安全关键信息**

> ### 对本项目的关键判断
> 必须**混合使用范式 1 + 范式 2，并对安全信息做「不可压缩」豁免**：
> - **单次会话**：全量重放 + 滑动窗口（保留最近 N 轮）+ 摘要节点（旧轮次压缩）
> - **跨天长期**：事实抽取 + 向量/图检索，沉淀 `UserProfile`（人格、应对方式、社会支持、触发源、既往风险史、量表趋势）
> - **安全红线**：任何涉及自杀/自伤/绝望表达的 turn **永不摘要、永不裁剪**，单独落 `risk_flags` 表，并在**每一次** LLM 调用时硬注入 system prompt（LangGraph 用节点、ADK 用 `before_model_callback`）

## 3. 【范式升级】Agent Harness Engineering：可靠性不在模型，在执行器

> **来源**：Junjie Li, Xi Xiao, Yunbei Zhang, Chen Liu et al.《Agent Harness Engineering: A Survey》，CMU / Yale / JHU / NEU / Tulane / UAB / Virginia Tech / Amazon 等 19 位作者，71 页，2026-05，投稿 TMLR。
> 论文主页 <https://picrew.github.io/LLM-Harness/> ｜ 配套开源目录 **Awesome-Agent-Harness** ｜ 编码样本 **138 个开源项目**

### 3.1 核心论断：Harness 正在成为绑定约束（Binding Constraint）

综述摘要的第一句是：**"The harness is becoming the binding constraint"** —— 生产环境中任务执行的可靠性，**更少取决于底层模型，更多取决于包裹模型的那层基础设施**，即 **Agent 执行器（harness）**。

一个对本项目方法论有直接影响的推论：

> **长时程任务的基准分数，是「模型–harness 配对」的属性，而不是模型单独的属性。**

落地成两条工程纪律：

1. **换模型必须做 harness 固定的对照实验。** 我们要验证「换更强模型能否降低漏报率」时，必须只变模型、不动工具 schema / 上下文装配 / 风险阈值 / 提示词，否则结论不可归因。
2. **先怀疑 harness，再怀疑模型。** 出现「识别不准」时，优先排查：工具描述是否清晰、风险词表是否覆盖、上下文是否把关键信号裁掉了、验证集是否有标注噪声 —— 而不是第一时间换模型。很多团队抱怨「模型不够强」时，真正的短板在工具设计、上下文策略、沙箱配置、验证机制与权限控制。

### 3.2 概念边界：Prompt / Context / Harness 是作用域外扩，不是阶段替代

| 层次 | 工程对象 | 回答的问题 |
|---|---|---|
| **Prompt Engineering** | 一次模型调用 | **怎么说**：指令、示例、输出格式、推理模板 |
| **Context Engineering** | 多步执行中的信息状态 | **每步看到什么**：检索、排序、过滤、摘要、窗口管理 |
| **Harness Engineering** | 闭环执行系统 | **谁维护状态、谁调工具、谁限权限、谁注入反馈、谁验证、谁记录、失败怎么恢复** |

> **Harness 的工作定义**：Agent 系统里**除模型权重之外的一切** —— 执行环境、工具接口、状态与记忆、生命周期编排、可观测、验证、治理。

**换成本项目的语言**：LangGraph 的图只是 harness 的 **L 一层**；§5 的记忆与 Schema 是 **C 层**；§8 的安全与风险分级是 **G 层**；§10 的评估方案是 **V 层**。**我们其实已经在做 harness 工程，只是此前没有按层命名。** 这一章的价值是给出一张不遗漏的清单。

### 3.3 ETCLOVG 七层分类法（综述的核心贡献）

前四层 = **结构核心**，后三层 = **控制面**。论文特别说明：相比早期「六组件」框架，这里把 **Observability 与 Governance 提升为独立层**，因为生产中它们各有独立工具栈、各自由不同团队负责。

| 层 | 名称 | 管什么 | 本项目的对应物 | 状态 |
|---|---|---|---|---|
| **E** | Execution environment | 代码在哪跑、边界是什么（托管沙箱 / microVM / 浏览器沙箱 / OS 权限） | 暂不涉及代码执行 | ⚪ 未启用 |
| **T** | Tool interface & protocol | 外部能力怎么被描述、发现、调用（MCP / A2A、工具描述与选择） | 危机干预工具（推热线、通知人工）、量表计分、证据检索 | 🟡 可用，描述需规范化 |
| **C** | Context & memory | 短期 / 会话级 / 持久化三个尺度上模型能看见什么 | `memory.py` 事实抽取 + 风险事实库 + 滚动摘要 + 不可压缩安全区 | 🟢 强项 |
| **L** | Lifecycle & orchestration | 读写状态的控制流 | LangGraph 状态图 + 条件边 + `interrupt()` | 🟢 已落地 |
| **O** | Observability | 轨迹、成本、故障、可靠性信号 | `audit_trace` 表有雏形 | 🟡 缺统一 trace 与成本/延迟面板 |
| **V** | Verification & evaluation | 把任务与轨迹变成评估、失败归因、回归反馈 | 仅有离线指标设想 | 🔴 **最薄弱** |
| **G** | Governance & security | 模型级 / 系统级 / 组织级三层约束 | 风险词表 + 审核台 | 🟡 缺标准化生命周期钩子 |

**几个必须记住的实证点：**

- **T 层投入产出比最高。** 论文引用的 harness-only 消融实验中，**只改工具格式与调用协议，编码基准改善可达 10 倍量级**。工具描述质量直接决定模型选错工具的概率。→ 本项目的「危机干预工具集」值得单独打磨描述与错误处理。
- **E 层远未解决。** 容器逃逸基准显示当前模型在特定配置下**逃逸成功率 15%–35%**。本项目暂不开放代码执行，但若未来引入（如让 Agent 生成情绪趋势图、跑统计脚本），必须单独设计沙箱与权限模型。
- **G 层靠生命周期钩子注入，不改 Agent 核心推理逻辑。** 这与本报告 §8.1「风险检测与对话生成解耦」的判断完全一致，且给出了更完整的钩子清单：

  | 钩子 | 位置 | 本项目用法 |
  |---|---|---|
  | 执行前 pre-execution | 输入进 LLM 前 | 硬注入 `risk_flags`、危机话术约束、非医疗定位声明 |
  | 调用前 pre-invocation | 工具调用执行前 | 「通知人工 / 推送热线」二次确认，防误触发 |
  | 执行后 post-execution | 工具输出回注上下文前 | 过滤自杀方法、手段可得性等禁止内容（对应 §8.4 红线 3） |
  | 人工介入 HITL | 高风险动作 | high / imminent 分支 `interrupt()` 挂起 |

### 3.4 生态分布：开源项目的层间不均

论文按「主层」对 **138 个开源项目**编码（多标签，主层 = 最核心机制）：

| 层 | **L** 编排 | V 验证 | E 执行 | O 可观测 | G 治理 | T 工具 | **C** 上下文 |
|---|---|---|---|---|---|---|---|
| 项目数 | **47** | 21 | 20 | 15 | 14 | 12 | **9** |

读法（对选型有直接意义）：

- **L 层密度最高 = 竞争最激烈，也最商品化。** §5.1 选 LangGraph 是对的，但要清醒：**编排层本身不构成本项目的壁垒**。真正的壁垒在 **C（纵向个性化记忆）** 与 **G（安全治理）**。
- **C 层项目最少，不代表不重要** —— 它通常嵌在更大框架内部（架构耦合的结果，不是需求缺失）。这恰好印证了 §0 把「长期记忆层」单列为独立选型的判断：**自建记忆层而非依赖框架内置，是正确决策**。
- **O 与 G 在开源中最薄**，更多活在商业平台 / SDK / 工程博客里。论文判断：**运维控制的成熟度晚于运行时和基准设施**。对心理健康这种高责任场景，这两层恰恰最不能省。

### 3.5 三个跨层张力（任何单层都解决不了）

**① 成本—质量—速度三角**
更细的权限、更完整的轨迹、更深的验证都提升质量，但代价是 token、延迟、基础设施。**质量不是可以独立最大化的标量** —— 必须决定哪些风险值得昂贵控制、哪些检查可以异步化或放进回归套件。
→ 本项目：三通道并集召回（§8.2）是**每轮都跑的贵检查**；PHQ-9 周复评、离线标注回归是**异步的便宜检查**。这个切分要显式写进设计文档，不要默认所有检查都同步执行。

**② 能力—控制权衡**
更多工具 → 覆盖面大，但工具选错与提示注入的攻击面也大；持久化记忆 → 支持跨天个性化，但引入隐私、过期信息与来源追溯问题。
→ 本项目：跨天画像是**必须**的能力（`baseline_emotion` 判定「相对恶化」），因此必须同时配：**事实来源追溯（`source` 字段）、过期标记（`updated_at` + 置信衰减）、用户可查看可删除**（数据合规）。这不是「开放 vs 封闭」的二选一，而是一条连续设计轴。

**③ Harness 耦合问题**
局部优化是脆弱的：工具描述占用上下文窗口 → 改变模型行为；执行环境通过包版本 / 延迟差异 → 影响验证结果；没有身份与权限状态的轨迹 → 不能作为治理证据。
→ **纪律：harness 的变更必须当系统级变更来测。** 改风险词表（T/G）→ 必须重跑离线回归（V）；改上下文裁剪阈值（C）→ 必须重测「危险信号是否被裁掉」（V+G）；改量表计分（T）→ 必须监控分级分布漂移（O）。

### 3.6 五个开放问题 → 本项目的对应动作

| # | 论文的开放问题 | 本项目的动作 |
|---|---|---|
| 1 | 执行环境的加固与扩展 | 暂不涉及；引入任何代码 / 文件执行前先补沙箱与权限模型 |
| 2 | 长程 Agent 的可靠状态管理：把上下文管理**从「字符串拼接」重构为状态估计问题** | ⭐ 已在做，继续加强：每条抽取事实加 `source` / `extracted_at` / 矛盾标记；恢复时**从持久化制品（`risk_flags`、量表时序）恢复，而不是从压缩后的摘要恢复** |
| 3 | 轨迹原生的故障诊断：trace 应成为计算 outcome、失败归因、回归测试的**首要对象** | ⭐ 见 §3.7 |
| 4 | 跨 Agent / 工具 / 人的标准交接协议 | 交接班（会话超长转交、转人工）时**不只传摘要**，要传：风险等级、未决决策、已给过的热线、轮次/预算状态、trace ID |
| 5 | 模型变强后的自适应简化：harness 每个组件都编码了「模型哪里不行」的假设 | 建立**定期消融机制**：每季度挑 2–3 个组件（如某些强制注入说明、上下文重置策略）做消融，模型升级后识别哪些从「承重结构」变成「纯开销」 |

### 3.7 【行动项】把 V 层补上：轨迹原生评估（Trace-native Evaluation）

论文对 V 层的核心主张：**trace 应该是评估的首要对象，而不只是事后调试材料。** 论文指出当下最具体的起点，正是「可观测性已普及、离线评估却很稀缺」这一落差 —— 与本项目现状吻合。

> **术语区分**：`trajectory` = 观察-动作-再观察的抽象序列；`trace` = 一次运行留下的**可审计记录**（模型输出、工具调用与返回、环境状态变化、上下文快照、错误、重试、恢复动作、token、延迟、成本）。这里是后者。

现有 `audit_trace` 表已具雏形，建议扩展为：

```sql
audit_trace(
  id, session_id, turn_id, node,
  model, model_version, prompt_hash,     -- 可归因到具体版本
  risk_level, risk_sources jsonb,        -- 三通道各自命中情况
  input_ctx jsonb,                       -- 当轮完整上下文快照（含是否命中不可压缩区）
  tools_called jsonb, tool_outputs jsonb,
  output jsonb,
  latency_ms, tokens_in, tokens_out, cost,
  error text, retry_count int,
  ts
)
```

从 trace 出发，按**三个维度**评估，而不是只看通过率：

| 维度 | 问什么 | 本项目的具体指标 |
|---|---|---|
| **结果正确性** | 最终做对了吗？ | 风险分级与临床标注的加权 Kappa（§10） |
| **路径合理性** | 是靠正确路径做对的吗？ | 是否走了危机协议、是否漏跑任一通道、是否靠重试刷过、每轮 token / 延迟成本 |
| **评估器可信度** | 评估本身可信吗？ | 多标注员一致性 Kappa、困难样本集（隐晦表达 / 反讽 / 方言 / 模态不一致）覆盖率 |

**为什么这对心理健康场景尤其关键**：论文的核心洞察是**单一通过率隐藏了太多变量**。一个「结果正确」的 Agent 完全可能是**走了不安全路径碰巧对了** —— 例如漏跑模型通道却靠规则兜住、或给了热线但语气冷漠、或钻了评测集漏洞。只看最终分级会漏掉这类缺陷，而这类缺陷在临床上正是事故前兆。

### 3.8 趋势判断：从框架（Framework）到平台（Platform）

- **框架**提供本地抽象：Agent、工具、记忆、执行循环。
- **平台**提供完整生产系统：持久化工作空间、托管沙箱、身份、计费、可观测、评估、治理、人工交接。

> 早期竞争围绕「谁能最快搭出 Agent 循环」；当前竞争围绕「谁能让循环长期稳定运行」。

→ 对本项目：不要指望换一个框架解决可靠性问题。要按 ETCLOVG 逐层自建/补齐，并把**编排层与记忆层解耦**（§12 风险 3 已提出）以保持可替换性。

### 3.9 补充：形式化模型、完备性矩阵与九大横切挑战

> 姊妹综述：Meng et al.《Agent Harness for LLM Agents: A Survey》—— 用形式化语言刻画同一个对象，可与 ETCLOVG 交叉印证。

#### ① 形式化六元组 `H = (E, T, C, S, L, V)`

| 符号 | 组件 | 职责 |
|---|---|---|
| E | 执行循环 | 观察–思考–行动循环、终止判定、错误恢复 |
| T | 工具注册表 | 类型化目录、路由、监控、schema 校验 |
| C | 上下文管理器 | 窗口管理、压缩、检索 |
| S | 状态存储 | 跨轮次/会话持久化、崩溃恢复 |
| L | 生命周期钩子 | 授权、日志、策略执行、埋点 |
| V | 评估接口 | 动作轨迹、中间状态、成功信号 |

**与 ETCLOVG 的映射**：**S 归入 ETCLOVG 的 C / L 层**；**O 与 G 是六元组未显式覆盖的额外控制面关注点**（即 §3.3 所说"论文把 O/G 提升为独立层"的由来）。

该模型用**标记转换系统（LTS）语义**区分两类属性，这个区分对本项目的治理设计很有用：

- **安全性属性（Safety）＝ 不变量**：任何时刻都不得违反。→ 本项目："风险相关表达永不进入摘要管道""high 以上必须人工审核""禁止输出自杀方法"。
- **活性属性（Liveness）＝ 最终进展保证**：系统最终必须往前走。→ 本项目："危机分支必须给出热线，不允许静默失败""每轮必须有分级结果，不允许卡住无响应"。

> 一句话：**安全性是"不能出错"，活性是"不能不动"。** 两者需要在 G 层同时约束 —— 只做安全护栏而没做降级兜底，会产出一个"什么都不敢说"的 Agent。

#### ② Harness 完备性矩阵（我们用的是哪一类）

| 类别 | 代表系统 | 特征 |
|---|---|---|
| **全栈 harness（各层齐备）** | Claude Code、AIOS、OpenHands、SWE-agent | 真正的生产级执行器 |
| 多智能体 harness | AutoGen、MetaGPT、CAMEL、ChatDev、DeepAgents | 协同强，但 E / C / V 层参差 |
| **通用编排框架** | **LangChain、LangGraph、LlamaIndex** | **只提供原语，完备性完全取决于使用者怎么拼** ← 我们在这一格 |
| 评估基础设施 | AgentBench、OSWorld、BrowserGym、HAL | 只覆盖 V 层，不是执行 harness |

**读法**：我们选的 LangGraph / LlamaIndex 属于第三格，意味着 §3.3 表里标 🔴/🟡 的 O / V / G 层**没有人为我们兜底**，必须自建。这与 §3.4 的生态密度结论一致。

#### ③ 九大横切挑战（附量化严重性）

| # | 挑战 | 关键数据 | 本项目相关性 |
|---|---|---|---|
| 1 | 安全与沙箱（E） | 容器逃逸率 **15%–35%**（SandboxEscapeBench） | 暂不开放代码执行；若未来引入需单独设计沙箱 |
| 2 | 评估与基准（V） | 自动化评估假阴性率约 **28%**（OSWorld）；通过 benchmark 的 PR 人工合并率低 24.2 pp，且每年扩大 9.6 pp | ⭐ 直接支持 §10「必须有专业人工标注集、不能只靠 LLM-as-judge」 |
| 3 | 协议标准化（T） | MCP（工具↔harness）**2–15 ms** vs A2A（agent↔agent）**50–200 ms**，差一个数量级 | 工具调用优先 MCP；本项目若做多评估者投票（§8）需评估延迟预算 |
| 4 | 运行时上下文管理（C） | 结构化技能注入 **+16.2 pp** | §6.1 上下文装配模板应进一步 **schema 化**、按相关性注入而非全量拼接 |
| 5 | 工具使用与注册表（T） | **删除 80% 工具 > 升级模型** | ⭐ 危机分支只保留 2–3 个工具（查热线 / 通知人工 / 触发干预） |
| 6 | 记忆架构（S/C） | 记忆压缩方案削减约 **90%** token；全上下文贵约 10× | 印证 §2.3 混合范式；但安全信息必须豁免压缩 |
| 7 | 规划与推理 | **接口设计的影响超过模型能力** | 印证 §3.1「先怀疑 harness，再怀疑模型」 |
| 8 | 多智能体协同 | 对抗性场景下**拜占庭容错仍未解决** | 若引入多评估者，采用**同构投票**而非对抗式辩论 |
| 9 | 计算经济学 | 平均 **1M token / 任务**（AgencyBench） | ⭐ 多模态原始数据绝不进上下文，感知层必须转结构化摘要（§6.1、§12 风险 4） |

#### ④ 可直接抄的实践原则

| 层 | 原则 |
|---|---|
| **T** 工具 | 从最小工具集开始，按需增加；用技能注入（C 层）门控暴露，而非全部塞进 schema |
| **C** 上下文 | 结构化 skill schema + 按相关性注入，反对穷举堆上下文 |
| **V** 验证 | 自动指标 + 人工验证集双轨，**绝不能只靠 LLM-as-judge** |
| **G** 治理 | 沙箱是硬性要求，纵深防御；高风险动作必须人工审批 |
| **S** 记忆 | 默认全上下文之前先评估压缩方案（全上下文贵约 10×） |
| 协议 | 工具调用优先 MCP；A2A 仅用于延迟可接受的多 Agent 场景 |
| 多智能体 | 生产环境避免对抗性拓扑 |

#### ⑤ 未来方向（可作为技术雷达长期跟踪）

1. **harness 规范 DSL**：形式化表达 harness 契约，支持自动合规检查
2. **跨 harness 基准可移植性**：同一测试套件无修改跑在任意合规 harness 上
3. **扩展安全分类法**：在 OWASP Top 10 之外补进工具劫持、上下文投毒、Agent 冒充
4. **MCP / A2A 互操作网关**
5. **长时程评估方法论**：面向 1M+ token 的持续任务
6. **Harness-aware 微调**：针对具体 harness 配置条件化训练模型（模型与 harness 协同进化）
7. **记忆接口标准化**：S 层可插拔后端统一 API（跨 Mem0 / LanceDB 等）
8. **Harness 透明性与可审计性**：把路由、压缩触发、工具选择等决策暴露给外部审计 —— 对心理健康这类高责任场景，是合规刚需

### 5.1 为什么是 LangGraph 而不是 CrewAI / AutoGen

| 判据 | 说明 |
|---|---|
| 流程是**确定性状态机**而非自由讨论 | 心理评估流程（评估→分级→分流→干预）步骤固定、分支明确，CrewAI/AutoGen 的「自主协商」在这里是**风险**而非优势 |
| 必须能**中途挂起等人工** | `interrupt()` 是原生一等公民，其他框架需 hack |
| 必须**可回放审计** | checkpointer 保存每步状态，出事故能精确复现当时上下文（合规/医疗责任） |
| 需要**精确控制上下文注入** | 「risk_flags 必须注入、绝不压缩」这种硬约束只有显式状态图能保证 |
| 需要**并行多模态证据处理** | `Send` API 做 map-reduce 式并行（多帧/多片段同时分析） |

### 5.2 为什么还要 LlamaIndex

LangGraph 不做检索与多模态索引。LlamaIndex 补的是：
- `MultiModalVectorStoreIndex`：视频帧 + 自述文本联合检索（例：「找出他上次也这样低落时说过什么」）
- `FactExtractionMemoryBlock`：自动把对话变成用户事实，天然实现"个性化"
- 两者可无缝拼：把 LlamaIndex 的 retriever/memory 包成 LangGraph 的一个节点即可。

## 6. 记忆与数据 Schema 建议

```sql
-- 用户长期画像（事实型记忆，可由 mem0 / LLM 抽取后写入）

scale_score(
  id, user_id, date, scale_name,    -- PHQ-9 / GAD-7 / C-SSRS / PSS ...
  item_scores jsonb, total_score int,

)

-- 【安全关键】风险事件，永不压缩、永不裁剪
risk_flag(
  id, user_id, session_id, ts,

  evidence text,                     -- 原文片段（保留原话）

  csssrs_dimension text,             -- 意念/计划/准备/行为/意图

-- 会话与审计
```

### 6.1 上下文装配模板（每轮注入什么）

```
[SYSTEM]
  角色与边界（非医疗诊断、危机时必须给热线）
  ── 强制注入区（不可省略/不可压缩）──
  当前风险等级：{risk_level}
  历史风险事件（最近 N 条原话）：{risk_flags}
  ─────────────────────────────
  用户画像：{user_profile 摘要}
  今日多模态观察：{modality_summary}
  量表趋势：PHQ-9 {今日} (上次 {上次}, 基线 {基线})，GAD-7 ...
  长期相关记忆（检索得到）：{retrieved_facts}
[HISTORY]
  历史摘要（早于最近 N 轮）：{rolling_summary}
  最近 N 轮原文：{recent_messages}
[USER]
  {当前输入}
```

**Token 预算建议**：强制注入区 ≤ 15%，画像+检索记忆 ≤ 25%，历史摘要 ≤ 15%，最近轮次 ≥ 35%，其余留给输出。

## 7. 情绪识别与个性化设计要点

1. **多模态融合放在感知层，不放在 LLM 里**
   视频/语音先由专用模型出结构化指标（表情分布、语速、停顿比、基频变化），再以文本摘要形式进上下文。理由：可解释、可缓存、token 便宜、可单独评估。
2. **相对变化 > 绝对数值**
   每个用户建立情绪基线（`baseline_emotion`），判断「相对于他自己的恶化」，避免个体差异导致误判。这正是「个性化」的核心价值。
3. **模态不一致本身是强信号**
   自述说"我挺好的" + 视频呈现平淡情感/语音低能量 → 触发更谨慎的探询路径（掩饰倾向）。这条规则应显式写进图里。
4. **量表用于校准，对话用于发现**
   量表（PHQ-9/GAD-7）作为 ground truth 校准模型输出；对话负责捕捉量表覆盖不到的内容（近期事件、关系冲突、失眠细节）。

## 8. 安全与风险分级设计（最关键章节）

### 8.1 架构原则：风险检测必须与对话生成解耦
2026 年该领域研究的明确建议是：**在架构上分离「风险检测」与「对话生成」**，由一个独立、保守的风险判定组件对每轮输入做判定，而不是让共情对话模型自己顺带判断。原因：
- 对话模型被优化为「共情、维持关系、避免冒犯」，这与「保守报警」目标冲突；
- 独立通道可以单独调阈值、单独评测、单独审计、单独升级，而不影响对话体验。

**落地方式**：在 LangGraph 里把 `risk_detector` 做成**与对话节点并行的独立分支**，其输出对主流程具有**否决权（veto）**。

### 8.2 三通道并集召回（宁误报，不漏报）

| 通道 | 内容 | 特点 |
|---|---|---|
| **规则通道** | 自杀/自伤词表、方法词、告别式表达、PHQ-9 第 9 题 > 0、C-SSRS 关键条目 | 零漏报底线，可解释 |
| **模型通道** | LLM/微调分类器做语义级判定（隐晦表达、隐喻、反讽、"托孤式"话语） | 覆盖规则漏掉的表达 |
| **多模态通道** | 语音平淡/哭泣/长停顿、表情钝化、近期量表急剧恶化 | 捕捉文本掩饰情况 |

**最终等级 = 三通道结果取最大值（并集升级，不允许降级）**。

### 8.3 分级与响应策略

| 等级 | 判定要点（参考 C-SSRS） | Agent 行为 |
|---|---|---|
| **none** | 无相关表达 | 常规情绪支持对话 |
| **low** | 有活着无意义感/被动死亡愿望，无意念 | CBT 引导（认知重构、行为激活）+ 加强关注；记录 flag |
| **moderate** | 有主动自杀意念，无具体计划 | CBT + **共同制定安全计划**（预警信号/应对策略/可联系的人/降低手段可得性）+ 主动提供热线 + 24-48h 内复评 + 通知运营 |
| **high** | 有计划 / 有准备行为 / 有一定意图 | **切换危机协议**：停止探索式提问，明确表达关心、直接给出热线与紧急联系人、鼓励立即求助；`interrupt()` 挂起等人工介入；推送给专业人员 |
| **imminent** | 正在实施 / 手段在手 / 明确即刻意图 | 最高优先级：给出紧急救援指引（120/110/危机热线），立即人工/机构介入，全程留痕 |

**危机热线（中国大陆，需按上线地区核实并配置为可维护的配置项）**
- 全国心理援助热线：**12356**（国家卫健委统一号码）
- 北京心理危机研究与干预中心：**010-82951332**
- 希望24热线：**400-161-9995**
- 紧急情况：**120**（医疗急救）/ **110**（公安）

### 8.4 不可妥协的工程红线

1. **风险相关内容永不进入摘要/压缩管道**，单独存储并每轮硬注入。
2. **不做自动化闭环**：high 以上必须有人工审核通道，产品上要有值班机制与 SLA。
3. **禁止输出内容**：具体自杀方法、手段可得性建议、对自杀行为的中立/美化描述 → 输出侧 Guardrail 拦截。
4. **降级兜底**：LLM 超时/异常/被拦截时，返回预设的安全兜底话术 + 热线，绝不静默失败。
5. **明确非医疗定位**：产品文案与 Agent 自述都要声明「不提供诊断与治疗，紧急情况请联系专业机构」，并有用户知情同意。
6. **数据合规**：心理数据属敏感个人信息 —— 加密存储、最小化采集、明确授权、可撤回、可删除；访问审计。
7. **全链路 trace**：每次风险判定保存输入上下文、模型版本、prompt 版本、输出（LangGraph checkpointer + 独立 `audit_trace` 表）。

## 9. CBT 疗愈对话子图设计（轻症路径）

把 CBT 会谈做成**子图（subgraph）**，而不是一段自由 prompt，便于评估与迭代：

```
情绪命名(affect labeling)
   → 情境澄清(发生了什么/何时/和谁)
   → 识别自动化思维(那一刻你脑子里想到什么)
   → 认知歪曲分类(灾难化/全或无/读心/过度概括…)
   → 苏格拉底式提问(证据支持/反对/替代解释)
   → 生成替代性想法
   → 行为激活 / 微行动承诺(今天可做的一件小事)
   → 会谈小结 + 反馈收集
```
- 每一步都是节点，允许**在任何节点被 risk_detector 打断**跳转到危机分支。
- 用 `State` 记录本次会谈进行到哪一步，跨天可续（"上次我们聊到…"）→ 强个性化体感。

## 10. 评估方案

| 模块 | 指标 | 目标 |
|---|---|---|
| 情绪识别 | 与量表得分的相关性（Pearson r）、分类 F1 | r ≥ 0.6 |
| **风险检测** | **召回率优先**（Recall / Sensitivity），其次 Precision、FPR | Recall ≥ 0.95（high 以上尽量 →1.0）；漏报为红线缺陷 |
| 风险分级 | 与临床标注（C-SSRS）的加权 Kappa | κ ≥ 0.6 |
| 对话质量 | 共情量表人工评分、会话完成率、用户满意度 | — |
| 干预效果 | PHQ-9 / GAD-7 前后测变化量、留存 | 显著下降 |
| 系统 | 端到端延迟、上下文 token 成本/轮、危机响应时延 | 危机响应 < 2s 给出热线 |

**必须做的**：建立含**专业标注**的离线评测集（含隐晦表达、反讽、方言、模态不一致等困难样本），每次 prompt/模型变更都跑回归。

> **补充（见 §3.7）**：评估对象应从「最终分级」升级为**完整 trace**。除**结果正确性**外，还要评估**路径合理性**（是否走了危机协议、是否漏跑任一通道、是否靠重试刷过、每轮 token/延迟成本）与**评估器可信度**（多标注员一致性、困难样本覆盖率）。
> 理由：单一通过率会掩盖「走了不安全路径碰巧做对」这类缺陷 —— 例如漏跑模型通道却靠规则兜住、或给了热线但语气冷漠。在心理健康场景下，这类缺陷正是事故前兆。
> 另需注意（§3.1）：**分数是「模型–harness 配对」的属性**。换模型评估时必须固定 harness（工具 schema、上下文装配、风险阈值、提示词）只变模型，否则结论不可归因。

## 12. 风险与开放问题

1. **漏报风险**：任何模型都会漏；必须有量表定期强制复评（如每周 PHQ-9）作为第二道网。
2. **过度依赖 Agent**：产品设计上要避免用户把 Agent 当成唯一支持来源，需引导真实社会支持。
3. **框架锁定**：编排层与记忆层解耦（记忆走自己的 service/表），未来可换框架。
4. **成本**：多模态分析成本高，建议每日离线批处理 + 对话时只用摘要。
5. **伦理审查**：涉及自杀风险的产品建议走伦理委员会/专业机构合作，明确责任边界。
6. **Harness 耦合**（见 §3.5③）：任何单层改动都可能改变整体系统行为 —— 改风险词表要重跑离线回归、改上下文裁剪阈值要重测「危险信号是否被裁掉」、改量表计分要监控分级分布漂移。**变更必须当系统级变更来测，不能在单层内做 A/B。**
7. **Harness 自适应简化**（见 §3.6 #5）：harness 的每个组件都编码了「模型哪里不行」的假设。模型升级后需**定期消融**，识别哪些组件已从「承重结构」退化为「纯开销」，避免长期背负无谓的延迟与成本。
8. **交接信息不完整**（见 §3.6 #4）：会话超长转交、转人工时，只传摘要会丢失关键状态。需标准化传递：风险等级、未决决策、已给过的热线、轮次/预算状态、trace ID。
